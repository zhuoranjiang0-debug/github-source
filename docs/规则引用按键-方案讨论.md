# 规则里怎么引用「屏幕按键」——方案讨论

> 这份文档是给团队看的：我们在哪、卡在哪个概念上、有哪两条路、建议走哪条。
> 阅读时间约 5 分钟。**这一条不阻塞任何事，可以先原样交付，只是想听听第二个人怎么看。**
>
> **2026-09-19 晚更新：已按方案 A 动手做完了**（队友还没回话，但这条改动小、
> 又可逆，就先做了；存档点见文末第七节，随时能退）。实现见下面第五节后的"实施结果"。

## 一、背景

屏幕按键（触屏上那几个方块按钮）已经做完，并且**归做游戏的人自己管**：
放几个、放哪、按下去等于按什么，都在属性面板里改，还能"复制一份"做出新键。

按键按下时做的事是：**按下对应的输入动作**（Godot 的 InputMap 动作名，
`ui_left` / `ui_right` / `ui_accept` …）。运行时是
`GameRuntime._press_action()` → `Input.action_press()`。

这样带来一个好处，而且是已经在平板上验证过的：
**键盘和触屏共用同一批规则。** 示例里左右移动的条件是「按住 `ui_left`」，
所以按键盘左方向键和按屏幕左键都能让恐龙动，不需要写两条规则。

## 二、问题

规则里要引用"按住哪个键"时，写的是**动作名**，而玩家/创作者在界面上看到的是这个：

> 当每一帧，如果「小恐龙」站在地上 且 正按住「**ui_accept**」，就让「小恐龙」跳起来

两个问题：

1. **看不出来是哪个键。** 屏幕左下角那个方块上面画着"跳"，规则里写的是 `ui_accept`，
   中间隔着"动作名"这一层。`ui_accept` 在引擎里的本意是"确认"，
   是我们自己在示例里把它当跳跃用的。
2. **写错不会有任何提示。** 这个参数是自由文本；校验器目前只校验语句类型、
   必填参数和对象选择器，**不校验这个键名是否存在**。填成 `ui_aceppt`
   不报错，规则只是永远不成立——排查起来像"按键坏了"。

## 三、两条路

### 方案 A：规则只引用"动作"，界面把动作显示成人话

「按住按键」的参数从自由文本变成下拉框，选项来自已有的动作表
（`RuleVocabulary.BUTTON_ACTIONS`，现在 7 条，带中文名），
界面显示"往左走 / 往右走 / 跳跃·确认"，存进 JSON 的仍是 `ui_accept`。

- 实现：词汇表里这个参数从 `string` 改成 `enum` 即可，规则面板会自动生成下拉框
  （现有机制，`rule_editor.gd` 里没有针对具体类型的代码）；再加一项校验 + 测试
- 保住：键盘和触屏共用同一批规则；复制出来的新键只要绑同一个动作就自动受规则管
- 缺点：中文名是我们起的，用户做"开火"时看到"跳跃·确认"会觉得不对味

### 方案 B：规则直接引用"某一个按键"（用户自己起的名字，比如「跳」）

规则里选的是工程里的某个按键对象，而不是动作名。

- 实现：界面上几乎白送（已经有"选一个对象类型""选场景里某个对象"两种现成下拉框）
- 致命项一：**键盘上失效。** 要判断"此刻是不是这个按键被按住"，
  只有触屏数得出来（哪根手指按在哪个方块上，对应 `_touch_buttons`）。
  键盘按空格时没有"某个方块被按住"这回事。除非退回按动作判断，
  那又分不清两个都绑 `ui_accept` 的键，绕一圈变回方案 A
- 致命项二：**换一关就断。** 按键是摆在某个关卡里的，规则引用的是那个关卡里的对象
- 致命项三：**复制出来的键不归规则管**，得再配一条一样的规则
  （和刚做完的"复制一份做新键"直接打架）
- 另外两个要额外回答的：一个动作被两个键绑着时显示谁的名字？
  工程里一个按键都没有（纯电脑上玩）时这条规则怎么写？

### 对比

| | 方案 A（引用动作） | 方案 B（引用按键） |
| --- | --- | --- |
| 界面改动 | 小（参数类型改一下） | 很小（现成下拉框） |
| 键盘与触屏共用规则 | 保住 | **失去** |
| 复制新键后是否自动生效 | 是 | 否，要再配规则 |
| 换关卡 | 不受影响 | 断 |
| 失败模式 | 名字不贴用户的话 | 玩到那一步才发现（换关、按键盘、复制键） |
| 顺手修掉"写错没提示" | 是 | 是 |

## 四、建议

**走方案 A，另外加一个很便宜的可选项**：下拉选项后面括一句
"你的「跳」键绑了它"，让用户既看得见自己起的名字，规则引用的仍然是动作。
不做也不影响正确性。

方案 B 的直觉（所见即所得）是对的，但它真正想解决的"看不懂 `ui_accept`"，
方案 A 已经解决了；而它换来的三个失败模式都是**玩到那一步才发现**的类型，
代价比界面那点工作量贵得多。

更远一点的想法（先不做，记一笔）：让用户**给输入动作起别名**，
工程里存一张 `ui_accept → "开火"` 的小表，屏幕按键面板和规则都用这个词。
那才是"用他自己的话"，但要配一个"编辑输入"的界面，属于加分项。

## 五、想听意见的三个点

1. 规则里的引用对象，长期应该是**动作**，还是**具体的按键对象**？
2. 方案 B 在"电脑上玩、屏幕上没有按键"时没法表达，这个代价能接受吗？
3. 有没有第三条路我们没想到？

### 实施结果（2026-09-19 晚，按方案 A）

- 「按住按键」的参数变成下拉框，选项是「往左走 / 往右走 / 往上走 / 往下走 /
  跳跃 / 返回 / 选择」，存进 JSON 的仍是 `ui_left` 这类动作名
- 「按下按键时」也一并改成下拉（空格 / 回车 / Esc / A / D / W / S / E / Q）
- 名字只写一处：屏幕按键的属性面板、规则的下拉、规则念出来的句子，三处同一个词
- 规则句子跟着变人话：以前读"正按住「ui_left」"，现在读"正按住「往左走」"
- 表里没有的值（手改过 JSON）不会被吞掉，下拉里会补一项"当前值：xxx"显示出来

顺带修了一处同源的显示错误：带「反向」的条件以前句子不念反面，
「松开方向键就停下」读出来是"正按住左、正按住右"，正好相反；
现在念"没有按住……"，并且条件块上补了那个一直缺失的「反向」勾选框。

**方案 B、以及"给输入动作起别名"仍然待定**，等队友的意见。

## 六、顺带发现（另一件事，同源）

示例里跳跃规则用的是**键盘事件**（`key_press` + `Space`），而左右移动用的是
**动作**（`key_held` + `ui_left`）。所以：手机/平板上按屏幕跳跃键没有反应，
按左右键正常——因为屏幕按键产生的是"动作按下"，不是键盘事件。

**这是示例自己两条规则写法不一致，不是屏幕按键坏了。**
要不要统一（以及顺带加一种"按下某个动作时"的触发），等这条讨论有结论一起定。
