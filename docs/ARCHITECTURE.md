# 架构设计

## 1. 产品定位

AI2D Game Creator 是一个**移动端优先**的 2D 游戏原型创作工具。它的目标用户是没有编程基础的游戏爱好者，使用场景是碎片化的：地铁上、课间、睡前想到一个点子，掏出手机十几分钟做个能跑的东西出来，发给朋友玩。

因此产品有一条不可动摇的约束：**编辑操作必须在触屏上成立**。任何需要精确鼠标操作、需要键盘输入代码、需要理解引擎概念的设计，都不属于这个产品。

需要明确的是本产品**不是**什么：

- 不是完整的游戏引擎，不追求做出可以商业发行的游戏
- 不是 AI 一键生成游戏，AI 是助手不是作者
- 不是 PC 工具的移动端移植，交互要重新设计

## 2. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 引擎 | Godot 4.x | 开源免费、2D 性能好、支持 Android/iOS/Web 导出、GDScript 上手快 |
| 语言 | GDScript | 与引擎零阻抗，学生团队维护成本最低 |
| 数据格式 | JSON | 人可读、易 diff、易分享、AI 可直接产出 |
| AI 接入 | HTTP + Provider 抽象层 | 供应商可替换，避免被单一 API 绑架 |

### 一条重要的架构决策：数据驱动

整个产品建立在**一个前提**上：**游戏原型 = 一份 JSON 文档**。

编辑器的全部工作就是修改这份 JSON；运行器的全部工作就是读取这份 JSON 并把它变成能玩的东西。

这个决策带来一连串好处，值得单独说明：

- 编辑器和运行器彻底解耦，可以各自独立演进、独立测试
- 保存、加载、撤销、分享、导出、版本管理全部退化成「处理 JSON」
- AI 模块不需要理解引擎，它只要产出合法的 JSON 就行
- 自动化测试可以在没有图形界面的情况下跑，逻辑正确性可以脱离引擎验证

代价是运行前要做一次「反序列化 → 构建场景树」的转换，但这个开销在原型阶段完全可以忽略。

## 4. 编辑器设计

### 4.1 界面布局（横屏）

```
┌──────────────────────────────────────────────┐
│  ← 返回   项目名        ▶ 运行    ⋯ 更多       │  顶栏
├──────────────────────────────────────────────┤
│                                              │
│                编辑画布                       │
│        （拖拽实体 / 双指缩放 / 单指平移）        │
│                                              │
├──────────────────────────────────────────────┤
│  🎨素材   ➕实体   ⚙属性   🧠AI   🔗逻辑       │  底部工具栏
└──────────────────────────────────────────────┘
```

面板以**底部抽屉（bottom sheet）**形式弹出，不遮挡画布时保持收起。屏幕小是移动端的根本约束，绝不做常驻的左右侧边栏。

### 4.2 核心交互

**放置实体**：底部工具栏「➕实体」→ 抽屉展开素材/实体库 → 按住拖到画布 → 松手落位。

**选中与移动**：单击选中，选中态显示包围框与四角控制点；拖动本体平移，拖控制点缩放，双指旋转。

**画布手势**：单指拖动空白处 = 平移；双指捏合 = 缩放。这与编辑器里「拖动实体」的手势冲突，需要用「起手是否命中实体」来消歧。

**撤销**：所有修改 JSON 的操作都走 `CommandStack`，顶栏提供撤销/重做。这是移动端编辑器的生命线——触屏误操作概率远高于鼠标。

### 4.3 关键风险：编辑器本身就是个大工程

Godot 自带编辑器**无法在手机上运行**，我们必须用 `Control` 节点从零写一套编辑 UI。这是本项目最大的工作量来源，也是最容易失控的地方。

应对策略：

1. **先桌面后移动**。先用鼠标键盘把功能跑通，再补触屏手势。开发效率高得多，而且桌面端本身就是有价值的形态。
2. **横屏优先**。竖屏手机做拖拽编辑体验极差，MVP 阶段明确只保证横屏平板与横屏手机。
3. **控件自建一套**。属性面板、抽屉、按钮统一封装成组件，避免每个功能重写一遍。

## 5. 运行器设计

运行器接收一份 `Project`，输出一棵可运行的场景树。

```
load_project(json) → ProjectModel
        ↓
  SceneBuilder.build(scene)  → 根据 Scene 里的实例列表生成节点
        ↓
  RuleEngine.attach(rules)   → 把规则挂到对应事件源上
        ↓
     游戏运行中……
```

### 规则引擎

规则引擎是整个产品「让非程序员也能写逻辑」的落点。采用**事件—条件—动作**（ECA）模型：

> 当 `触发事件` 发生，如果 `满足全部条件`，就执行 `这些动作`。

这个模型的好处是它与自然语言几乎同构，用户看一眼就懂；同时它又足够表达绝大多数原型级玩法。

规则示例——「碰到金币就加分并销毁金币」：

```json
{
  "trigger": { "type": "collision", "a": "tag:player", "b": "tag:coin" },
  "conditions": [],
  "actions": [
    { "type": "change_property", "target": "tag:player", "property": "score", "delta": 1 },
    { "type": "destroy", "target": "other" }
  ]
}
```

完整的事件、条件、动作清单见 [DATA_MODEL.md](DATA_MODEL.md)。

## 6. AI 服务层

AI 的定位是**创作助手**，不是自动生成器。产品里它承担四件事：

1. 生成角色/道具的静态 sprite
2. 生成关卡布局建议
3. 根据一句话描述生成规则草稿
4. 参数推荐（速度、跳跃力、敌人数量等手感参数）

### Provider 抽象

```
AIService (接口)
├─ MockProvider      离线、确定性、零成本 —— 开发与演示的默认实现
├─ OpenAICompatProvider   兼容 OpenAI 协议的任意服务
└─ DomesticProvider  豆包 / 通义 / 智谱 等国内服务
```

**MockProvider 不是权宜之计，而是有意为之的设计。** 它让整个 AI 链路在没有 API Key、没有网络的情况下也能端到端跑通和演示，这在比赛答辩、断网教室、以及控制调用成本时价值极高。真实 Provider 只是替换掉实现而已。

### 一个必须正视的技术边界

计划书里写了「角色外观与简单动画的自动生成」。需要坦白地说：**AI 生成前后连贯、可直接使用的逐帧动画序列，目前业界并不成熟**，硬做会掉进一个填不平的坑。

MVP 阶段建议把 AI 能力收窄为：

- 生成静态角色 sprite（成熟、可靠）
- 生成同一角色的配色/风格变体（成熟）
- 动画交给**参数化方案**：缩放、旋转、位移、换色、上下浮动、挤压拉伸

这样既守住了「AI 降低美术门槛」的核心卖点，又避开了不可控的技术风险。等基础版本稳定后，再评估接入骨骼动画方案。

## 7. 分享与导出

原型做出来要能立刻给别人玩。三条路径，按投入排序：

1. **项目文件导出**：把 JSON 与素材打包成 `.ai2d` 文件，本地保存或发送。最简单，先做这个。
2. **分享链接 / 二维码**：上传到服务端，扫码打开网页版直接玩。技术上依赖 Godot 的 Web 导出（WASM），是「扫码即玩」的关键。
3. **导出独立包**：导出 Android APK。属于锦上添花，放最后。

注意路径 2 的体量：Godot Web 导出的 WASM 首包通常有几 MB 到十几 MB，移动网络下需要加载提示。这一点要在设计时就考虑进去。

## 9. 开发原则

1. **数据模型是契约。** 任何改动都要同步更新 [DATA_MODEL.md](DATA_MODEL.md)、Schema 和示例工程，并跑通校验脚本。
2. **逻辑与界面分离。** 数据层的所有逻辑必须能脱离 Godot 的渲染与输入独立验证。
3. **垂直切片优先。** 宁可「一个功能从编辑到运行完全跑通」，也不要「十个功能各完成一半」。
4. **每个里程碑末尾必须能演示。** 能演示的进度才是真进度。
