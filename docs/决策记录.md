# 决策记录

这份文件存在的唯一目的：**让项目的记忆不依赖任何人，也不依赖任何 AI。**

换会话、换人接手、隔三个月再回来，从下往上读一遍就能接上。

## 怎么用

- **做了决定就加一行。**不用写长，写清"决定了什么、为什么"就够。
- **想改某个决定时不要删旧的**，新加一行，并注明它取代了哪一条。知道"以前为什么不是这样"和知道"现在是什么"一样重要。
- 接手项目的人（包括未来的你）从最后一行往前读。

| 2026-09-18 | 退出试玩同时提供**键盘与按钮**两条路 | 用户报告真实窗口里 Esc 无反应，但自动化测试里正常。在无法复现的情况下，与其赌某一个输入路径，不如给一条必然会成功的路 | 按键处理挪到输入链首站 `_input`，右上角另加「返回编辑」按钮 |
| 2026-09-18 | 窗口尺寸**全程只设定一次**，切换模式不改 | 用户报告「试玩后屏幕上同时残留大块旧画面和小块新画面，最小化再还原才刷新」。根因是切模式时改了窗口大小：Godot 的视口尺寸立刻变了，系统窗口还没跟上，中间那块就残留着旧帧 | 试玩画面改为居中留边，不再缩放窗口；新增测试锁死「切模式不改变窗口尺寸」 |
| 2026-09-18 | 游戏画面**不做任何偏移**，一律从窗口左上角画起 | 上一条改成「居中留边」后，用户报「试玩里什么都没有，只剩分数和生命」。居中要算 `(窗口尺寸 - 画布尺寸) / 2`，而窗口尺寸在显示缩放、系统裁剪、最大化时会虚大，偏移把整个游戏推出了可视区。用截图工具在 1920×1080 下复现成功 | 好看让位于可靠；新增测试锁死运行器位置必须为零 |
| 2026-09-18 | 颜色改为**实例级覆盖**（`instances[].color`） | 属性面板要能"把这枚金币改成红色"。但颜色原本只存在实体定义（类型）上，一改就是所有金币一起变，需求在数据层面无法表达 | 实例自己设了颜色就用自己的，留空则跟随类型；"跟随类型"按钮可清除覆盖 |
| 2026-09-18 | 缩放**同时作用于碰撞体** | 视觉缩放而碰撞体不缩放的话，"把平台拉宽"只是看起来宽，玩起来对不上——这类"看起来对、玩起来错"的问题最难查 | 碰撞体尺寸按实例缩放计算；新增测试断言拉宽后碰撞体真的变宽 |
| 2026-09-18 | 圆形的横纵缩放产生**椭圆**，且三处表现必须一致 | 用户发现"金币纵向调大，半径不变"。查下去发现同一个圆在三处各不相同：编辑器画布只乘了横向缩放、运行器画面缩成了椭圆、碰撞体取了横纵平均。三处不一致，用户永远猜不准自己在改什么 | 画布用多边形画椭圆、运行器画面对应、碰撞体用多边形逼近（Godot 2D 没有椭圆图元）；点选判定也改为椭圆，矩形同时补上了缩放 |
| 2026-09-18 | 撤销之后**尽量保住选中状态** | 用户报「连续调大小后按 Ctrl+Z，一步退回，但属性面板也关了」。撤销是把整份工程从快照重建，我顺手把选中项一并清空。可用户按撤销往往是想"改回去接着调"，面板一关反而多出一步 | 撤销后对象若仍存在则保留选中；只有对象确实不存在了（撤销的是"放置"）才清空 |
| 2026-09-18 | 编辑器快捷键放在**输入链第一站** `_input` | 用户报「输入 1.1 后直接按 Ctrl+Z，数字变成 1.」。输入框自带"文字撤销"，把 Ctrl+Z 抢走了，编辑器的撤销根本没轮到 —— 同一个快捷键在焦点不同时意思不一样，用户不可能猜得中 | Ctrl+Z / Ctrl+Y / Ctrl+S / F5 移到 `_input`；撤销前先让输入框交出焦点，把没提交的内容落定。Delete 仍留在 `_unhandled_input`（在框里按 Delete 应该是删字符） |
| 2026-09-18 | **撤销**上一条：快捷键退回 `_unhandled_input` | 上一条改动引入的新行为（输入框里全选删除后再打字、按 Ctrl+Z 会保留新值并丢失选中）比原来的小毛病更让人困惑，而且在没有真实键盘的环境里无法验证。用户实测后判断"上一个版本完全够用"，这个判断是对的 | 恢复原样。代价是：焦点在输入框里时 Ctrl+Z 仍是文字撤销，先按回车或点开别处即可。**小毛病有天然绕法时，不值得拿稳定性去换** |
| 2026-09-18 | 逻辑编辑器**占满整块编辑区**，不塞进侧栏 | 一条规则有「事件 + 若干条件 + 若干动作」，侧栏放不下；而且「编辑关卡」和「编辑逻辑」是两个不同的心智模式，分开比混在一起清楚。将来搬去手机，这个界面直接就是全屏页 | 顶栏加「逻辑」按钮切换；回到关卡编辑时画布状态不变 |
| 2026-09-18 | 规则参数的表单**全部从词汇表生成** | 词汇表里已经声明了每个参数的名称、类型、默认值、取值范围。照着生成控件，新增一种动作就只需要改词汇表，界面代码一行不动 | `rule_editor.gd` 里没有针对任何具体动作的代码 |
| 2026-09-18 | 每条规则都要能**复述成一句中文**，且模板也是数据 | 用户配完需要能读回来检查——「非编程用户友好」最直接的体现。复述模板和词汇表分两张表，用一条测试保证一一对应，新增动作忘了补模板会立刻报错 | 规则清单和详情页都显示这句话 |
| 2026-09-18 | 复述时**标签念实体的名字**，不念标签本身 | 句子里写「player」对一个做游戏原型的人毫无意义；写「小恐龙」他一眼就懂。标签是给程序看的，名字是给人看的 | 下拉框和句子都用实体名字 |
| 2026-09-19 | 移动端**以横屏平板为主场**，手机定位为「能装、能跑、能玩」 | 量出来的账：按钮放大到触屏该有的大小后，手机横屏的上下两条工具栏要吃掉**一半高度**，画布只能缩到一半；平板只占四分之一，几乎不受影响。手机上无论怎么排都很挤，而平板的屏幕面积是手机的两倍多 | 布局结构不改；只做触屏手势 + 按钮放大。手机不承诺关卡编辑体验 |
| 2026-09-19 | **不做**「底部抽屉」和「收起侧栏」 | 抽屉那套（容器、开合、页签）是最大的一块工作量，而它在手机上也只能做到"不那么差"。收起侧栏更没用：手机上挤的是**高度**不是宽度，把侧栏收掉画布一点也不会变大 | 省下的是整个方案 C 的工作量 |
| 2026-09-19 | 屏幕按键**由做游戏的人自己定**：放几个、放哪、按下去等于按什么，都在属性面板里改 | 按键不是我们的功能，是他的游戏的一部分。我们预置三个键，等于替他决定"你的游戏只能左右移动加跳"。他也应该有办法做第四个键 | 属性面板给按键多一节「按键绑定」；位置大小沿用普通对象的拖动与缩放；配合「复制一份」就能做出新键 |
| 2026-09-19 | 按键绑定的动作写进**词汇表**（`RuleVocabulary.BUTTON_ACTIONS`），界面和运行器读同一份 | 下拉框里的选项文字、按键上画的箭头、按键上写的字，三处必须是同一个来源。分成两处写，迟早出现"面板上选的是跳跃、按键上写着左" | 新增一种可用动作只改词汇表一个文件 |
| 2026-09-19 | 下拉框念人话（"往左走"），不念引擎的动作 id（`ui_left`） | 做原型的人不该为了放一个左移键去查引擎的动作表。表里没有的动作（手改过 JSON）就把 id 原样显示出来——看得懂看不懂是一回事，看不见就一定会以为没绑上 | 下拉框显示中文名；按键上写什么字也跟着动作走 |
| 2026-09-19 | 按键上写的字**跟绑定的动作**，不跟实体类型的名字 | 用户的真实用法是"复制一个键出来改成别的"。复制"左"改成跳跃，如果字还写着"左"，屏幕上写着左、按下去却是跳，他会认为程序坏了 | 方向动作画箭头，其它动作写词汇表里的短名字；表外动作退回实体名 |
| 2026-09-19 | 规则里引用按键改成**下拉框**，不再手打（方案 A） | 原来是个空输入框，要手打 `ui_accept`。两个毛病：看不出那是屏幕上哪个键；**填错了不会有任何提示**（校验器只管语句类型和对象选择器，不管这个键名存不存在），规则只是永远不成立，排查起来像按键坏了 | 「按住按键」「按下按键时」的参数都变成可选项；想打错都难 |
| 2026-09-19 | 规则的按键名和屏幕按键**共用一套说法**，只写一处 | 同一个动作会出现在三个地方：按键属性面板的下拉、规则里的下拉、规则念出来的句子。分成几处各写各的，迟早出现"面板上叫跳跃、规则里叫 ui_accept" | 名字集中在 `ACTION_PARAM_LABELS`，屏幕按键的动作表从它取；有测试盯着两边不许漂 |
| 2026-09-19 | 键盘实体键和输入动作**分成两张表** | 它们不是一回事：动作（`ui_accept`）是屏幕按键也能触发的；键盘实体键（`Space`）只有真的按键盘才触发。混在一张表里，用户会以为屏幕按键能当空格用 | 规则的"按住按键"只列动作；"按下按键时"只列键盘键 |
| 2026-09-19 | 勾了「反向」的条件，句子要念成反面，并补上勾选框 | 「松开方向键就停下」实际是"两个方向都没按住"，可句子读出来是"正按住左、正按住右"——**正好相反**。这种"看着相反"的规则比看不懂更糟。另外编辑器里一直没有那个勾选框，只有手改 JSON 才能设 | 新增反向念法表（每种条件各一句，compare 靠翻运算符）；条件块上出现「反向（不满足）」勾选框 |
| 2026-09-19 | 跳不到的那条跳跃规则，选择**只在示例里补一条**，不给引擎加新事件 | 屏幕按键只按下输入动作，而示例的跳跃规则盯的是键盘事件，于是平板上按了没反应。两条路：给引擎加一种"按下某个动作时"的事件（更通用，但要动引擎），或者在示例里补一条"每一帧 + 正按住跳跃 + 站在地上 → 跳"（用现有积木搭）。用户选后者：**逻辑上不会出问题，改动只在示例** | 示例多一条规则（11 条）；代价是"按住跳跃键会连着跳"，且规则清单里跳跃相关有三条，看着有点重复 |
| 2026-09-19 | 词汇表**瘦身**：删掉 3 项 | 下拉栏太长影响体验。删的是两类：**被取代的**（条件「按住屏幕某侧」——屏幕按键做强之后没人再用它，而且它和"点屏幕跳跃"天生打架）和**说了做不到的**（动作「播放动画」——没有动画系统，只是记了个名字；「播放音效」——素材系统没落地，没有任何音效文件可放）。都是用户选了也看不出效果的项 | 条件 8 → 7 项，动作 14 → 12 项；连带删掉运行器里的半屏判定与音效代码，以及相应测试 |
| 2026-09-20 | 极低概率的"跳得特别高"**暂不修** | 平板实测时偶发：点跳跃偶尔跳得异常高。用户判断改动风险大于收益，且演示时看不出来。**原因未定性**：同一帧触发两次跳跃其实不会跳更高（`jump` 是直接把速度设成同一个值），所以更像"空中又跳了一次"（二段跳），但没测出触发条件 | 记进「已知的粗糙处」，不列为缺陷。真要修，最稳的做法是给跳跃加一个很短的冷却（只改规则，不碰引擎），但那会改变手感，先不做 |
| 2026-09-20 | **绝不把 API key 打进要分发的程序里** | 编译进客户端的 key 一定能被扒出来（APK、网页版都一样）。泄露之后别人拿去随便刷，账单无法控制、也无法追。这不是成本问题，是"能不能把工具交给别人用"的问题 | 分发给同学/老师的包里永远不含 key |
| 2026-09-20 | 产品形态定为「**默认离线，可选自带 key**」 | 默认走离线生成：不联网、不花钱、断网照样能演（答辩现场网络不可靠）。想用真模型时，由**使用者填自己的 key**，谁的 key 花谁的钱，我们零成本 | 离线生成是保命的那条；在线只是加分。key 只存在使用者的本机，**绝不写进工程文件**（工程是要发给别人的，写进去等于跟着泄露） |
