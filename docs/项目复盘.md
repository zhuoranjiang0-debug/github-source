# 项目复盘

> 这份文档有两个用途：给我们自己看，知道走过哪些路；
> 也给结题报告的「项目过程」章节当素材。

## 一、五天做了什么

从 2026-09-16 晚到 09-20，分五段推进。

### 第一段：09-16 深夜 ── 09-17 凌晨

定架构、造地基。

- 定下**数据驱动**：一个游戏原型 = 一份 JSON
- 写出数据模型、读写、语义校验
- 写出**事件—条件—动作**规则引擎
- 示例「跳跃小恐龙」真的可以玩了
- 补上持续输入，让它能真正通关
- 加上双击即玩的启动入口

一夜之间从零到「能玩」。

### 第二段：09-17 深夜

补工程基础。

- 支持命令行指定工程，做出专门给人改的练习工程
- **修复了一次真实的文件编码事故**，并加入编码体检
- 整理文件夹
- 写下**决策记录**——让项目的记忆不依赖任何人，也不依赖任何 AI
- 把编辑器编码固定成 UTF-8

这一段没做新功能，但决定的是「这个项目能不能被别人接手」。

### 第三段：09-18 下午到深夜（19 次提交，9 小时）

从「能玩别人做好的游戏」推进到「**能从零做一个游戏，而且不用碰 JSON**」。

**下午：M2 编辑器最小闭环**

- 拖对象进画布、拖动摆位、撤销重做、保存、按 F5 试玩
- 紧接着连续修掉四个问题：F5 是哑的（信号漏接）、切换模式画面残留、
  试玩里什么都看不见、退出试玩回不来

**晚上：M2 收尾 + M3 逻辑编辑器**

- 属性面板：改颜色、大小、自定义数值
- 圆形对象的横纵缩放改成椭圆（此前画布、画面、碰撞三处表现各不相同）
- 撤销不再关掉属性面板
- **M3 逻辑编辑器**：左边规则清单每条都念成一句人话，
  右边用「当……如果……就……」配规则，表单全部由词汇表生成
- 又修掉三个问题：规则乱触发、换事件类型后参数栏不出现、撤销会丢选中

**当天结束时**：测试从 77 项涨到 244 项，代码 5644 行。

### 这段路里最有价值的一条经验

当天修掉的问题里，**绝大多数属于同一类：界面看上去完全正常，底下却没发生该发生的事。**

- 信号漏接了 → 按钮点下去没反应，界面上一切如常
- 下拉框回调参数个数错了 → 选项文字换了，数据没变，参数栏不出现
- 相切不算相交 → 「碰到敌人」规则永远不触发，代码看不出问题
- 画布、画面、碰撞三处各自算形状 → 用户改完看到的和玩到的不是一回事

这类问题**只能靠人真的去用**才能发现。当天用户报了 7 个问题，
其中 5 个是真 bug —— 命中率高得惊人，而且每一个的描述都直接指向了根因。

### 另一条：测试要能失败才有价值

当天出现过一条「连了监听、写了注释说『验证运行请求』、然后什么都没断言」的假测试。
它装作覆盖了运行按钮那条路径，实际什么都没验，于是信号漏接的 bug 一路溜到用户手上。

还有一次反过来：测试通过了，但因为它漏了「先点击画布」这一步，
结论和真实操作不符。**测试写得像那么回事，比没有测试更危险。**

### 第四段：09-19 全天（21 次提交）——从「电脑上能用」到「手机上能玩」

这一天的主线是**把做出来的游戏搬到手机/平板上**，外带把规则里一个说不清的概念捋顺。

**下午：先把移动端这件事想清楚**

- 写《移动端适配方案讨论》，量了按钮的实际物理尺寸：手机上要放大 2.4 倍才够手指点，
  平板只差 1.25 倍。结论是**以横屏平板为主场**，不做底部抽屉那一套
- 编辑器补触屏手势：单指平移、双指捏合缩放、触屏点选带容差
- 网页版跑通（导出、中文字体、一键构建），紧接着修掉网页版"点哪儿都对不上"的坐标偏差
- README 补接手须知：引擎去哪下、改文件前必须知道的编码坑

**傍晚：把游戏真的搬到手机上**

- 打通安卓打包，产出可安装的 APK。两个坑：必须开 ETC2/ASTC 纹理压缩，
  否则引擎判定"配置无效"**且不给任何原因**；Gradle 官方源在国内实测几十 KB/s，
  改用不开 Gradle 的打包方式
- 修正屏幕方向（一直设成了竖屏，桌面上完全看不出来）
- 修掉画面比例不对、屏幕上左右各留黑边
- **屏幕按键**：手机上终于能玩自己做的游戏。此前用"按住屏幕左半边就当向左走"，
  这个办法和"点屏幕跳跃"天生打架——用户实测"一开始移动就跳一下"

**晚上：按键归创作者管 + 平板实测**

- 屏幕按键能在属性面板里改绑定、复制出新键；**按键上写的字跟着绑定的动作走**
  （复制一个「左」键改成跳跃，它写"跳"而不是继续写"左"）
- 平板实测结果：**画面铺满 ✅、左右键正常 ✅、跳跃键按了没反应**
  根因查明：示例的跳跃规则盯的是**键盘事件**，而屏幕按键只按下**输入动作**
- 写了一份给团队看的方案讨论（规则该引用"动作"还是"某个具体按键"）
- **第一次打存档点**：两个 git 标签 + 一份《存档记录》，
  让人用大白话描述"回到改规则按键之前/之后"，不必记技术名

**深夜：把那个说不清的概念捋顺**

- 规则里"按住哪个键"从**手打 `ui_accept`** 改成**下拉框**，选项是人话（往左走 / 跳跃…），
  并且和按键属性面板共用同一套说法。手打填错以前**不会有任何提示**，
  规则只是永远不成立，排查起来像"按键坏了"
- 顺手修掉一处**"看着相反"**的显示错误：带「反向」的条件以前句子不念反面，
  于是"松开方向键就停下"读出来是"正按住左、正按住右"，与实际正好相反；
  编辑器里还一直没有那个勾选框，现在补上了
- 词汇表瘦身：删掉**被取代的**（按住屏幕某侧）和**说了做不到的**（播放动画、播放音效）
  共 3 项。后两个是"用户选了也看不出效果"的项，摆在下拉栏里属于骗人
- 示例补一条「按住跳跃键跳起来」——平板上的跳跃键终于能用（代价：按住不放会连着跳）
- 打了一个能直接发给同学的试玩包（85 MB，含引擎和中文字体）+ 一份《试用说明》

### 这一天留下的经验（多一半是给我的）

1. **"说了要做"和"真做了"是两件事。** 我说了句"现在重打安卓包"就结束了回复，
   用户以为我还在干活，其实那一步根本没跑。**规矩：凡是说"现在去做"的动作，
   必须在同一轮里做完并报出结果。**
2. **GUI 程序不等待。** Godot 的 exe 是图形界面子系统程序，直接调用时 shell 立刻返回、
   输出还是乱序的——因此误判过一次"截图没生成"。改用 `Start-Process -Wait` 并重定向输出。
3. **工具自己也有坑。** 自动截图工具默认会在第 88 帧点一下屏幕空白处，
   而这一下会把"选中的对象"清掉——第一次截图失败就是这个原因。
4. **别拿体积当"有没有更新"的证据。** 重打安卓包后字节数和上一版**完全一样**，
   一度怀疑新代码没装进去。做了敏感性验证（改一个字号再导一次，哈希立刻变了），
   才确认导出确实跟着源码走。体积不变只是因为打包有对齐填充。

### 第五段：09-20 —— AI 助手开了个头（M4 第一块）

这一天先把「AI 到底怎么做」想清楚，再动手。想清楚的部分比代码重要：

- **产品形态定为「默认离线，可选自带 key」**：默认不联网、不花钱、断网能演；
  想用真模型的人填自己的 key。**key 绝不写进工程、绝不打进分发的包**——
  打进客户端的 key 一定能被扒出来，账单会失控。
  统一接口按 OpenAI 兼容格式设计，将来在线厂商和本地模型走同一条路
- **离线那层不是"非智能"，是"只会认几种说法、但绝不出错"**：
  认不出来会老实说认不出来，而不是编一个看起来对的答案

动完手之后，工具会做两件事：

> 「一个会飞的紫色小怪」→ 生成一种敌人、摆进关卡、自动接上扣血规则
> 「每 2 秒掉一个金币」→ 生成一条定时掉金币的规则

流程上守住了四条，每条都是"敢让它动手"的前提：

1. **草稿先给人看**：它打算改哪几处，一条条列出来，人点头才动
2. **先在一份副本上试装、跑过校验才写进真工程**：不合法就连碰都不碰
3. **一步可撤销**：对象类型 + 实例 + 规则，按一次 `Ctrl+Z` 全撤掉
4. **确定性**：同一句话问两次，结果一模一样（随机 id 改成数数）。
   演示时"每次都不一样"会让人怀疑这东西稳不稳

还有一个细节值得单独记：生成的敌人**打的是工程里已有的 `hazard` 标签**，
于是示例里那条「碰到尖刺扣血」自动就管到它了 —— 草稿会明说"不会再加规则，
你工程里已有的那条会管到新敌人"。**AI 先看一眼工程现状、能复用的就复用**，
比它多写一条一模一样的规则要有用得多。

顺带踢掉一个自己造的坑：第一版给敌人加了 `hp: 2`，但没有任何规则会让敌人受伤。
这和前一天删掉的「播放动画」是同一种毛病 —— 看起来有、实际什么也不影响。
删掉了。

**同一天又被用户抓到一个同类问题**：AI 生成的"天上掉金币"，金币生成在屏幕外、
而且根本不会往下掉。根因是**生成出来的东西不会自动受重力** ——
示例里的金币为了不挡住玩家，物理类型是 `none`。我的草稿文案却写着"会掉下来"。

修法上有两个选择：给原金币加重力（但那会让示例里摆好的 5 枚金币当场全掉下去），
或者**复制一份"长得一样但受重力"的金币**。选了后者 ——
AI 帮忙改东西，不该顺手把用户已经摆好的关卡改掉。

这件事的教训是：**只断言数据不够，得让运行器真跑一遍**。
现在那条测试会启动运行器、等金币生成出来、再断言它的 y 坐标真的在变大。

**同一天下午，用户又连着提了三件交互上的问题**，都做了：

1. **叠在一起的对象选不到下面那个。** 两个金币完全摞在一块时，点哪儿都只选中
   上面那枚。改成"在同一个地方再点一下，就往下钻一层"（到底绕回最上面），
   状态栏同时告诉你"这里叠着 2 个，这是第 1 个"。平板没有 Alt 键，
   所以不能用"Alt+点击"那种解法。
2. **规则里选对象，五枚金币都叫「金币（这一份）」**，一模一样，挑不出来。
   现在带编号和位置：「金币 #3 · 700, 300」，并且折到"就这一个对象"分组里，
   上面一组是"所有这一类"（多数规则要的是这个）。
3. **"自身"到底指谁。** 这一条查下去发现的问题比界面标签大得多：
   在「每一帧」「点击屏幕」这类事件里，引擎**根本没有触发对象**，
   选「自身」的规则会永远不生效 —— 而界面一声不吭。
   现在界面上不列它（换一句说明为什么没有），校验器再拦一道，
   手改 JSON 也躲不过。**这是个藏了很久的静默失效，靠"用户看不懂"才挖出来。**

顺着第 2、3 条还改了金币的行为：**拾取物不互相挡、也不挡玩家**（只和地面碰）。
金币挡金币本来就没道理——它是拿来捡的，不是拿来当积木的。
但判定"碰到没有"靠的是触发区，不能跟着一起关，否则金币会变成"看得见吃不到"。
这一条专门写了测试：把玩家挪到金币身上，分数必须真的加。

**当天傍晚，用户把这两批（AI 助手 J1~J10、三件交互 K1~K12）一次走完，
全部通过，没有发现新问题。** 测试记录里各留了一行 —— 那份清单现在
覆盖到了 470 项自动化测试 + 十几轮人工实测，可以直接当结题材料的测试报告。

**晚上又出了一件很典型的**：用户给 AI 生成的小怪配了一条"设置速度"的规则，
小怪纹丝不动。查下去是两个原因：

1. 动作里填的是「自身」，而事件是「游戏开始时」—— 这个事件**没有触发对象**，
   `self` 指不到任何东西。界面其实已经把这一项藏起来了（下拉里显示
   "当前值：self（其他选项里没有）"），但**校验器认出的问题没有任何地方显示**，
   所以用户看不到"这条规则永远不会生效"。现在逻辑界面里会标 ⚠ 并写出原因。
2. 更要紧的是：那只小怪的物理类型是**"静止"**，而静止对象根本不参与物理步进 ——
   速度写进去了，没有任何东西去用它。物理属性写在**类型**上，而界面上改不了类型。

于是又补了两块：属性面板多了「**会动吗**」一节（跟随类型 / 静止 / 会飞 / 会掉，
实例级可改），AI 生成的飞行怪默认就是"会动"的。

这一连串事情的共同点是：**问题都不是"功能没做"，而是"做了之后用户看不出它有没有生效"。**
校验器能认出问题却没人看得见、物理属性写了却没人用、下拉里那个"其他选项里没有"
只是一行小字 —— 三处都是"信息存在但不出现"。这类问题只有真人在用的时候才会撞出来。

**当天最后一件：把"这一类"做成能改的**（用户提的"对象不在画布上时没法设置属性"）。
以前颜色、碰撞、会不会动只能按一个个对象改；现在点底部素材栏里的一项，
右边就切成「这一类」的面板（名字、标签、颜色、原始大小、碰撞、会不会动）。

设计上有两处是**专门为"别改错"做的**，值得记下来：

- **同一件事不许有两个词**：类型上叫「原始大小」（它本来多大），实例上叫「缩放」
  （这一个放大了几倍）。两处都能让对象变大，用词一混用户永远分不清。
- **两组界面互相指路**：类型面板写"只想改某一个？在画布上选中它"，
  实例面板写"想一次改一整类？点上面的「改这一类」"。与其让用户背规则，
  不如让他照着提示走永远是对的。

顺带定下一条界面风格：**分组标题（基本/外观/物理/数据）** —— 以后「属性清单」
加进来直接沿用，不至于长成两套界面。

## 三、现在的产品能做什么

用大白话说，它能做三件事：

**给人做游戏。** 从底部素材栏拖一个对象到画布、拖动摆位置、撤销重做，按 F5 立刻试玩，按 Ctrl+S 存成文件。**全程不碰 JSON。**

**让人看懂游戏。** 打开一份 `.ai2d.json`，里面写着玩家有多少血、金币在哪、碰到尖刺会怎样。不需要读代码就能明白这个游戏怎么运作。

**当场演示「改一下、立刻看到」。** 改颜色、挪位置、按 F5，效果立刻出现。这是答辩时最有说服力的三十秒。

## 四、六个真正重要的决定

完整的清单在[决策记录](决策记录.md)，这里挑出影响最大的六个。

### 1. 数据驱动：一个原型 = 一份 JSON

编辑器的全部工作就是修改这份 JSON；运行器的全部工作就是读取它并变成能玩的东西。

带来的好处是连锁的：保存、加载、撤销、分享、导出全部退化成「处理 JSON」；AI 模块不需要理解引擎，只要产出合法的 JSON 就行。

### 2. 逻辑用「事件—条件—动作」模型

> 当「点击屏幕」，如果「玩家站在地上」，就「让玩家跳起来」。

这个模型与自然语言几乎同构，不懂编程的人看一眼就懂。它直接对应计划书里「非编程用户友好的逻辑表达机制」这一条研究内容。

### 3. 词汇表用数据声明，界面从它自动生成

所有事件、条件、动作的类型和参数写在**一个文件**里。编辑器的表单从它生成，校验器拿它当白名单。

后果是：**新增一种动作只改一个文件，不用碰任何界面代码。** 这是让动作数量能持续增长而不拖垮开发速度的关键。

### 4. 目标定为「结题够用」档

团队会议的决定。编辑器只做「能拖、能跑、能存」，不追求功能完整。

这个决定让三天能做出一个可演示的闭环，而不是铺开十个各完成一半的功能。

### 5. 编辑与试玩共用同一份数据

点运行能看到刚改的东西，不必先存盘。存盘是「保存成果」，不是「预览的前提」。

### 6. 可靠性优先于美观

窗口尺寸全程只设定一次；游戏画面不做任何偏移。

这两条都是被真实故障逼出来的（见下节第 5 条）。凡是「为了好看」而增加的复杂度，只要有可能把主流程搞坏，就不做。

## 五、踩过的坑

这一节是整份复盘里最值得读的部分。**五个坑，五个都是「代码看起来完全正常」的那一类。**

### 1. 静止对象也在跑物理

玩家跳到地面上时两者有轻微重叠，地面自己去做解穿插，被一点点推下去，玩家跟着一起沉。

测试里第一次跑出来：玩家和地面一起掉了 320 像素。

**教训**：静止对象根本不该参与物理步进。现在的做法是只有运动对象才调用 `move_and_slide()`。

### 2. 碰撞只在「相交」时报告，「相切」不算

两个固体碰在一起时只是刚好贴上，形状并不相交。所以「玩家碰到敌人」这类规则**永远不会触发**，而代码看起来毫无问题。

**教训**：给触发区外扩 4 像素，实体一贴上规则就能感知到。

### 3. 编辑器用错编码，把汉字悄悄写坏

在编辑器里改完工程文件保存时用了 GBK，两个汉字被写坏。**JSON 结构依然合法、程序照跑不误**，只有游戏里的文字变了样——靠肉眼基本发现不了。

**教训**：读取前做字节级体检，并把编码固定进项目配置。测试里也加了一条编码检查，并且用人为破坏验证过它真的能抓到。

### 4. 信号漏接，而测试是假的

运行按钮和 F5 都是哑的——信号发出去了，但没人接。

更值得说的是：我为这条路径写的测试**连了监听、写了注释说「验证运行请求」，然后什么都没断言**。它长得像一条测试，实际什么都没验。

**教训**：测试必须能失败才有价值。现在那条测试改成真断言，另外加了一条走完整输入链路的整体测试。

### 5. 为了好看，引入了新故障

修复「切换模式时画面残留」时，顺手加了个「把游戏画面居中」的偏移量。结果在显示缩放或窗口最大化的情况下，这个偏移把整个游戏推出了可视区——用户看到的是「试玩里什么都没有，只剩分数和生命」。

**教训**：与修复无关的美观改动要单独做，不和功能修复混在一起。凡是新增的复杂度，先问一句「它会不会把主流程搞坏」。

## 六、这套协作方式本身

三天的推进靠的不是某个人记住了什么，而是一条规矩：

> **文件优先于记忆。** 重要的东西写进仓库，不留在对话里。

具体是四件事：

- 每个决定都写进[决策记录](决策记录.md)，包括「为什么」和「影响」
- 代码注释解释**为什么这么写**，而不只是「这行在做什么」
- 每次提交的说明里写清改动的原因
- 每个阶段的成果必须**能演示**，而不是「完成了一半」

这样做的直接好处是：换人接手、隔三个月再回来、甚至换一个 AI 助手，读一遍文档就能接上。
